# Hugging Face Model Upload Plan

## Goal

Allow an RLX run to automatically publish its trained model artifact to Hugging Face when the user has configured a Hugging Face token and the selected `rlx.toml` entry opts into publishing.

This should work for Prime RL runs without requiring users to manually SSH into the pod and push artifacts themselves.

## Assumptions

- Users will provide a Hugging Face access token through RLX settings.
- RLX will store that token in AWS Secrets Manager, using the same pattern as the existing W&B API key flow.
- Publishing is an RLX concern, not a Prime RL concern, so the publish settings should live in `rlx.toml`, not in the Prime RL config file.
- Most RL runs will be LoRA runs, so the default published artifact should be the adapter checkpoint, not a merged full model.
- The publish target should default to a collision-safe generated repo name when the user does not specify one explicitly.

## Proposed `rlx.toml` Shape

Add an optional Hugging Face block under each named RLX config entry:

```toml
[grpo-f1]
description = "GRPO reinforcement learning"
config = "configs/grpo-f1.toml"

[grpo-f1.huggingface]
enabled = true
repo = "13point5-labs/grpo-f1" # optional
visibility = "private"         # optional: private | public
collision = "suffix"           # optional: suffix | fail
artifact = "adapter"           # optional: adapter | full
```

Behavior:

- If `enabled` is false or absent, RLX does nothing.
- If `repo` is provided, RLX uses it as the base repo id.
- If `repo` is omitted, RLX generates one from project, config, and run identity.
- If `collision = "suffix"`, RLX appends a suffix when the repo already exists.
- If `collision = "fail"`, RLX stops with a clear publish error instead of creating a variant name.
- `artifact = "adapter"` is the default for LoRA runs.
- `artifact = "full"` is only used if we explicitly support merged/full export later.

## Naming Strategy

Recommended default:

- Base slug: `{repo_name}-{config_name}`
- Final generated id: `{hf_username_or_org}/{base-slug}-r{run_id}`

Examples:

- explicit base repo with suffix:
  - requested: `13point5-labs/ascii-align-qwen3-4b`
  - collision result: `13point5-labs/ascii-align-qwen3-4b-r184`
- fully autogenerated:
  - `13point5-labs/ascii-align-env-qwen3-4b-e3-alpha-256-r184`

Why use run id:

- it is already unique inside RLX
- it avoids timestamp-based ambiguity
- it makes backtracking from a Hugging Face repo to an RLX run straightforward

## Secret Handling

Add a Hugging Face token flow parallel to W&B:

- secret name: `rlx/huggingface-token/{clerk_user_id}`
- API endpoints:
  - `GET /api/huggingface-token`
  - `POST /api/huggingface-token`
  - `DELETE /api/huggingface-token`
- UI:
  - new Settings section for Hugging Face token status and replacement

Rules:

- never store the raw token in Postgres
- inject it only into the publish job environment
- redact it from all logged commands
- do not pass it into the main training job unless needed later for gated model downloads

## Artifact Source

RLX should publish from Prime RL weight checkpoints, not from the transient broadcast directory.

Preferred source:

- `outputs/weights/step_<n>`

Why:

- this is the stable Hugging Face-compatible checkpoint path used by Prime RL evaluation
- it is the right artifact boundary for later reuse and benchmarking
- it is less incidental than `outputs/broadcasts/...`

Important constraint:

- Prime RL only writes `outputs/weights/step_<n>` when `ckpt.weights` is enabled

Because of that, RLX should automatically ensure publish-enabled runs have weight checkpoints turned on.

## Launch Overlay Strategy

Do not ask users to manually add checkpoint-publish plumbing to every training config.

Instead, when Hugging Face publishing is enabled for an RLX config:

1. RLX generates a temporary overlay TOML at launch time.
2. The overlay enables checkpointing with weight checkpoint output.
3. RLX launches Prime RL against the merged config.

Minimum overlay behavior:

- enable `ckpt`
- enable `ckpt.weights`
- keep the final weight checkpoint

This keeps publishability an RLX-level feature and avoids mutating user repo files.

## Publish Job Lifecycle

### Run creation

At run creation time:

- parse `rlx.toml`
- resolve Hugging Face publish settings
- create the normal Prime RL jobs
- create an additional `CUSTOM_COMMAND` publish job after the launch job when publishing is enabled

### After training succeeds

The publish job should:

1. fetch the user’s Hugging Face token from AWS Secrets Manager
2. resolve the final stable weight checkpoint under `outputs/weights/`
3. determine the target repo id
4. create the repo if needed
5. upload the checkpoint folder contents
6. optionally upload a generated `README.md` model card
7. persist the final repo URL and repo id onto `run.monitoring`

### If training fails

- do not run the publish job
- mark the publish job as skipped or blocked by dependency

### If publish fails

- the run remains successful
- only the publish job fails
- surface the publish error clearly in the run UI

## Publish Implementation

Use the Python Hugging Face Hub client inside the pod-side publish job.

Reasoning:

- `transformers` already pulls in `huggingface_hub`
- Python API is easier to make idempotent than shelling out to the CLI
- easier to attach metadata and create repos programmatically

Rough flow:

```python
from huggingface_hub import HfApi

api = HfApi(token=os.environ["HF_TOKEN"])
api.create_repo(repo_id=repo_id, private=is_private, exist_ok=True)
api.upload_folder(
    repo_id=repo_id,
    folder_path=weights_path,
    commit_message=f"Upload RLX run {run_id} checkpoint",
)
```

## Metadata to Persist on the Run

Add a Hugging Face section under `run.monitoring`:

```json
{
  "huggingface": {
    "repo_id": "13point5-labs/ascii-align-env-qwen3-4b-e3-alpha-256-r184",
    "url": "https://huggingface.co/13point5-labs/ascii-align-env-qwen3-4b-e3-alpha-256-r184",
    "artifact": "adapter",
    "step": 300
  }
}
```

This lets the run page show a direct button to the published model.

## Adapter vs Full Model

### V1 recommendation

Publish adapter checkpoints only.

Why:

- RLX runs commonly use LoRA
- adapter upload is smaller and faster
- it matches the actual trained artifact
- it avoids expensive model merge/export work on the training pod

### Later option

Support `artifact = "full"` by adding an explicit merge/export step before upload.

That should be deferred until there is a concrete need, because it adds:

- more disk usage
- more runtime
- more implementation complexity

## Failure Modes to Handle

- missing Hugging Face token
- no `outputs/weights/step_*` produced
- repo already exists and `collision = "fail"`
- token lacks repo create/write permission
- upload partially succeeds and must be retried idempotently

Desired behavior:

- these failures affect the publish job only
- they must not rewrite the run itself to `FAILED`

## Minimal Backend Changes

- extend `RlxConfigEntry` with a nested Hugging Face publish config
- add Hugging Face token secret helpers in `aws_secrets_manager.py`
- add a Hugging Face settings router similar to the W&B router
- extend run resolution to carry publish config into job creation
- add a post-run publish job template
- extend command env injection to support `HF_TOKEN`
- persist Hugging Face repo metadata into `run.monitoring`

## Unit Test Coverage

- `rlx.toml` parsing and validation for the new Hugging Face block
- repo id generation and suffix behavior
- publish job creation only when enabled
- missing-token behavior
- upload source path resolution from `outputs/weights/`
- run monitoring merge behavior for published repo metadata

## Rollout Plan

### Phase 1

- automatic adapter upload for successful Prime RL runs
- token in settings
- direct Hugging Face button on run page

### Phase 2

- manual retry button for failed publish jobs
- optional public/private toggle in UI
- generated model card with config, run link, and W&B links

### Phase 3

- optional merged full-model export
- optional upload of eval artifacts and example generations

## Open Questions

- Should public/private visibility be controlled only from `rlx.toml`, or also overridable in the UI?
- Should we allow publishing intermediate checkpoints, or only the final one?
- Do we want one repo per run, or one repo per experiment family with branches/tags?

My recommendation for V1:

- one repo per run
- automatic suffix-safe naming
- final adapter checkpoint only
- configuration driven entirely by `rlx.toml`
